# linxh-extension-review · 浏览器插件五段式评估

## 什么时候用

用户抛来一个浏览器插件 / 谷歌扩展 / 油猴脚本 / 网页采集小工具的想法，哪怕只有一句话，**先别急着写代码**。按下面五段式跑，每一段之间用户要拍板，**AI 必须停下来等回应**，不能一路冲到底。

触发信号（用户常用说法）：
- 「我想做一个谷歌浏览器插件，功能是…」
- 「帮我做个 Chrome 插件 / Edge 插件」
- 「写个油猴脚本，自动…」
- 「做个工具，把某网站的内容抓下来 / 一键下载 / 自动…」
- 「写个浏览器自动化 / 一键 XX 的扩展」

**不触发**：已经评估过、用户拍板「就这么做」「直接写代码」「开始」「按这个做」，那是执行阶段，按正常开发走。

## 重要原则（所有段都适用）

**用户大多数不会编程，听不懂专业术语**。所有输出必须做到：

1. **大白话翻译铁律**：技术词可以出现（如 manifest、Service Worker、CSP、token），但**每段输出末尾必须用一句大白话翻译**告诉用户「你接下来要做什么 / 点哪里 / 看到什么」。
2. **步骤化操作**：让用户做事时，用「你点这里 → 弹出 X → 你在这里输入 Y → 按这个按钮 → 你会看到 Z」的格式，不用行话。
3. **拍板必带兜底两行**：每次列完 A／B／C 选项，固定加：
   - 「不确定？回『按推荐来』，我直接用推荐选项做。」
   - 「有别的想法？告诉我具体怎么改。」
4. **三个明确停顿点**：第 1、3、4 段末尾必须打「**等你回。**」三个字，防止 AI 一路冲到底。

---

## 五段式总览

| 段 | 干什么 | 谁说话 | 停不停 |
|---|---|---|---|
| 1 | 分类 + 澄清问答 | AI 问、用户答 | 问完停 |
| 2 | 五维评估 + 决策卡 | AI 输出 | 不停，连第 3 段 |
| 3 | 拍板项 + 推荐 | AI 列、用户选 | 列完停 |
| 4 | 执行方案 | AI 出方案 | 出完停 |
| 5 | 开干 | AI 执行 | — |

---

## 第 1 段 · 分类 + 澄清问答

**1.1** 把需求归到 5 类之一（采集 / 自动化操作 / UI 增强 / 监控通知 / 内容增强转换）。识别规则见 `references/extension-types.md`。

**1.2** 按类型挑 **3-5 个关键缺口问题** 问用户。
- 问题模板和按类型分组的问题库在 `references/question-bank.md`。
- **所有问题必须用 A／B／C 选项 + 一句话权衡 + 推荐项**，不要开放式问。
- 默认值能定的就别问，只问「不澄清没法评估」的需求缺口。
- **这一段只问需求缺口，不问实施决策**（实施决策留到第 3 段）。
- **列完问题固定加兜底两行**（见上面原则 3）。

输出格式：
```
这是个【采集型】插件，我先问 3 个需求点（都有推荐）：

1、**触发方式**？
   A：打开页面自动跑（省一步但容易误触发）
   B：点按钮主动跑（推荐：可控、不打扰）
   C：定时后台跑（最省事但要常驻服务）

2、…

3、…

不确定？回「按推荐来」，我直接用推荐选项做。
有别的想法？告诉我具体怎么改。

回完我跑五维评估。**等你回。**
```

---

## 第 2 段 · 五维评估 + 决策卡

用户回完第 1 段，按下面五个维度输出，每个维度一个小标题，结论先行、不灌水。完了直接接决策卡，**不停**。

**每个维度末尾必须用一句大白话翻译**（见上面原则 1）。

**维度一 · 这插件到底要做什么**
- 复述功能：用 AI 自己的话讲一遍要做什么，具体到「在哪个网站、点哪个按钮、抓什么数据、输出成什么」。
- 点破真实目的：往上想一层用户做这个是为了达成什么。
- 大白话翻译：「翻译一下：你做这个，本质上是想 XX」。

**维度二 · 怎么做（实现方案）**
- 形态：浏览器插件 / 油猴脚本 / 要不要本地后台服务，按 `extension-types.md` 的「形态建议」走。
- 关键技术点：怎么拿数据、要不要登录态、数据怎么导出。
- 大概工作量：一个下午 / 两三天 / 一周以上。
- **复用项目**：去 `references/reusable-assets.md`（若存在 `_personal-assets.md` 优先读那份）按需求类型匹配，明确说「复用 X 项目的 Y 文件／方案」，别只点名。没匹配上就说「这块要从零写」。
- 大白话翻译：「翻译一下：这个东西大致是用浏览器装个小程序 + 后台跑个小工具，预计花 X 时间」。

**维度三 · 难点和卡点**
- 命门：最容易卡死的那一步是什么，标出来。
- 维护卡点：目标网站改版就失效、需要持续跟着改。
- 别报喜不报忧。
- 大白话翻译：「翻译一下：这事最容易卡在 XX 这一步，如果过不去整个项目就废」。

**维度四 · 风险系数**
- 总评级用 **纯文字**「高 / 中 / 低」，**禁止用 emoji 颜色**（色盲安全考虑）。
- 分项：封号风险 / 平台风控限流 / 法律合规风险。
- 涉及色情、违规量产内容时坦诚说明性质、不搭专用自动化。
- 一句话结论：风险能不能接受、怎么压低。
- 大白话翻译：「翻译一下：做这个会不会被网站封、会不会有法律问题、做完能不能放心用」。

**维度五 · 有没有更好的形态**
- 现成工具？市面上的扩展 / SaaS / CLI 直接用就别造轮子，给名字。
- 更轻的形式？油猴脚本 / 一个 Python 小脚本 / 命令行工具 / 浏览器书签 / 自动化平台是不是更省事。
- 根本不用做？目的能用别的路径达成，插件是伪需求。
- 插件确实最优 → 明说「就该做插件」，给理由。
- 大白话翻译：「翻译一下：不一定非得做插件，XX 方案可能更省事 / 插件确实是最优」。

**决策卡**（紧接五维输出）：
```
═══ 决策卡 ═══
做不做     ：值得做 / 不值得做 / 换成 XX 形态
工作量     ：约 X 个半天
风险       ：高 / 中 / 低
推荐 MVP   ：先做能验证最关键一步的最小版本（一句话）
替代方案   ：如果不做插件，最优替代是 XX（一句话）
```

输出完决策卡 **直接接第 3 段拍板项**，不要停。

## 第 3 段 · 拍板项 + 推荐

基于第 2 段评估结果，列出**需要用户做选择的实施决策**，每项给推荐。

**跟第 1 段的分工**：
- 第 1 段问「需求缺口」（不知道需求长啥样就没法评估）。
- 第 3 段问「实施决策」（评估完了，有几个关键路径要用户拍）。
- **不要重复**，第 1 段问过的别再问。

**典型拍板项**（按需求挑 3-5 个，不是全部都问）：

| 类别 | 拍板项示例 |
|---|---|
| 范围 | MVP 砍到哪个版本（最小可跑 / 半成品 / 完整功能） |
| 复用 | 复用现有 X 项目还是新写 |
| 平台 | 只做 Mac 还是要兼容 Win |
| 时间 | 现在就开始 / 先做关键验证再决定 / 排队等其它项目 |
| 输出 | 数据存哪、文件名怎么命名 |
| 通知 | 走哪条 IM 通道、还是不通知 |
| 风险 | 用主号还是建小号 / 降频策略接受到哪一档 |
| 触发 | 手动按钮 / 自动定时 / 两者结合 |

输出格式：
```
我有几个点要你拍板（每个都给了推荐）：

1、**MVP 范围**？
   A：先抓 10 条纯文字跑通整条流程（推荐：半天能见效，验证最关键一步）
   B：直接做全量带图片
   C：先做能预览不下载的版本

2、**复用路径**？
   A：扩现有「XXX」项目加批量入口（推荐：省 70% 工作量）
   B：新开项目

3、…

不确定？回「按推荐来」，我直接用推荐选项做。
有别的想法？告诉我具体怎么改。

回完我给执行方案。**等你回。**
```

## 第 4 段 · 执行方案

用户拍完板，输出可执行的方案。**必须包含 4 件事，每件事都用大白话**：

**4.1 · 会做哪些东西**（原「文件清单」，用大白话）

列出要新建 / 要改的文件和它们的作用，每个文件加一句「这个文件管什么」的大白话说明。

```
要新建的（都在 ~/Projects/xxx/）：
  manifest.json   ← 插件的「身份证」，告诉浏览器这是什么插件
  popup.html      ← 你点插件图标后弹出来的那个小窗
  popup.js        ← 小窗里按钮的逻辑（点了按钮做什么）
  background.js   ← 插件的「后台小帮手」（你看不见，但一直在跑）
  server.py       ← 本地的小后台（在你电脑上跑，负责抓数据）

借现有项目的代码（不动原项目，只抄一份）：
  从「XXX 项目」抄启动脚本
  从「YYY 项目」抄某段功能

数据存哪：
  ~/Downloads/xxx/<日期>/  ← 文件夹会自动建好，里面是抓到的内容
```

**4.2 · 分几步做**（原「时间盒」，用大白话）

拆成 N 步，每步 ≤ 2 小时，每步给「做啥 + 怎么验证这步过了」。

```
第 0 步（10 分钟）· 跑一个小测试，确认能拿到数据
  → 你要做的：复制下面那段代码到终端跑，截图给我
  → 算过的标准：你看到结果里有「拿到 5 条」

第 1 步（30 分钟）· 我把本地后台先搭起来
  → 你要做的：等我做完，按提示在终端跑一条命令
  → 算过的标准：你看到「服务已启动 端口 18785」

第 2 步（45 分钟）· 我把插件框架搭起来
  → 你要做的：按我说的「打开 chrome://extensions/ → 开发者模式 → 加载已解压扩展程序 → 选项目文件夹」
  → 算过的标准：浏览器右上角出现新插件图标

第 3 步（45 分钟）· 我把改写功能接上
  → 你要做的：等我做完
  → 算过的标准：点插件图标，按抓取，几分钟后弹出文件夹，里面有 10 个文件

第 4 步（30 分钟）· 把整条流程跑通一次给你看
  → 你要做的：跟着我一起跑一次，验证
  → 算过的标准：见 4.4 的清单

总时长：约 X 小时
```

**4.3 · Step 0 关键验证**（原「命门验证」，用大白话）

从 `references/command-tests.md` 挑 1-2 条最相关的，把代码贴出来，配大白话指令：

```
第 0 步·关键验证（10 分钟，必须先跑过这个才往下做）

你只需要做 3 件事：
1、复制下面这一整段
2、打开「终端」app（在 macOS 启动台搜「终端」）
3、把复制的粘进去，按回车，截图给我

[贴具体可复制代码]

3 种可能的结果：
- 你看到「拿到 5 条」+ 5 行内容 → 关键验证通过，我接着做第 1 步
- 你看到「Failed to connect」 → 网络代理有问题，告诉我，我换值
- 你看到「429」或一堆 HTML → 网站这边有阻拦，回去重选 MVP
```

**4.4 · 做完啥样算搞定**（原「验收标准」，用大白话）

```
做完的标准（这 5 条都满足了才算搞定）：

1、浏览器右上角看得到插件图标
2、点图标弹出来一个小窗，里面有输入框和「抓取」按钮
3、点抓取，几分钟内小窗里能看到「抓取中 → 改写中 → 完成」的进度
4、完成后电脑自动弹出一个文件夹 ~/Downloads/xxx/<今天日期>/
5、文件夹里有 10 个 .md 文件，随便点开一个，能看到：原标题、原链接、原文、改写稿
```

**收尾**：
```
方案就这样。

不确定？回「按推荐来」，我直接按这个方案做。
有别的想法？告诉我哪里改。

确认就开干（说「开干」或「OK 做」），我从第 0 步关键验证开始。

**等你回。**
```

## 第 5 段 · 开干

用户说「开干」「OK」「按这个做」之后，按第 4 段方案逐步执行：

- **每步用环境提供的任务跟踪工具记录进度**（Claude Code 用 TodoWrite，Codex 用 plan update，其他环境用等价机制），做完打钩、报一句「第 N 步完成，验收：XX」。
- **每步报告时用大白话**：「我刚才做了 XX，下一步你要 YY」，别只说技术细节。
- **遇到方案外的决策**（比如关键验证失败、目标网站结构跟预期不一样）**立刻停下报告**，不要自作主张换方案。
- **每步做完留一个 commit**（如果项目是 git repo），提交信息用「[第 N 步] 做了 XX」。
- **第 0 步关键验证失败就回第 3 段**，不要硬上。

## 输出铁律汇总

- 结论先行、不铺垫、不问「我们继续吗」。
- 中文叙述用全角标点，禁破折号。
- 禁套路话（「实不相瞒」「真正的杀器」「封神」「划重点」）。
- 状态色 / 风险评级用「高 / 中 / 低」纯文字，不用 emoji 颜色（色盲安全）。
- 英文术语首次出现带中文翻译，格式 `English Term（中文意思）`。
- 第 1、3、4 段末尾必须打「**等你回。**」明确停顿。
- **每段技术输出末尾必须用一句大白话翻译**，告诉用户「你要做什么 / 看到什么」。
- **每次列 A／B／C 后必须加兜底两行**：「不确定？回『按推荐来』。」「有别的想法？告诉我。」
